## BUG-001 (daedalus v0.5.0) — Null `usage` on SSE final chunk discards streamed response

**Severity:** High — silently breaks task execution on streaming paths.

**Status:** ✅ **FIXED in daedalus v0.5.1** (2026-07-17). Upstream
cited our bug ID (`§BUG-001`) in the fix's comment block and
extracted the gatekeeper logic to a new `is_usage_only_chunk()`
helper in `MiniMaxSseParser.h` so the truth table is unit-testable.

**Affects:** `daedalus::LLMClient` SSE streaming path. Triggered
specifically by LLM providers that emit `"usage": null` on the final
SSE chunk (confirmed with MiniMax).

**Discovered in icarus:** 2026-07-17 (Phase 6 of CodeMax.md).

### Symptom (in icarus)

User gives the agent a task that requires a tool call (e.g. "list the
files in the current directory using the bash tool"). The agent:

1. Streams a tool-call delta through `on_assistant_delta`.
2. Receives the final SSE chunk from the server with `choices: []`
   and `usage: null` (this is the MiniMax "usage-only" trailer).
3. Emits the warning:
   ```
   [Warn] [LLM] 'usage' is null in SSE stream — token counts unavailable
   ```
4. Returns to the prompt without ever calling the tool.

From the user's perspective, the agent "stopped dead in its tracks"
after the warning, the task is not done, and no error is reported.
If the user retries, the same sequence repeats.

### Root cause

**File:** `daedalus-src/src/api/LLMClient.cpp`
**Lines:** ~1411-1417

```cpp
if (!response_json.contains("choices") || response_json["choices"].empty()) {
    bool is_usage_only_chunk =
        config_.stream &&
        response_json.contains("usage") &&
        !response_json["usage"].is_null();      // ← BUG
    if (is_usage_only_chunk) {
        // Recover the assistant message that the SSE parser
        // already accumulated from earlier delta chunks.
        json synth_message = sse_parser.synthesized_message();
        response_json["choices"] = json::array({
            {{"index", 0},
             {"message", synth_message},
             {"finish_reason", "stop"}}
        });
        // ... fall through to normal processing ...
    }
    else
    {
        // WRONG PATH TAKEN when usage is null:
        LOG_ERROR("No choices in response - will retry API call...");
        // ... 3-retry exponential backoff, 1s+2s+4s = 7s of spinning ...
    }
}
```

The condition `!response_json["usage"].is_null()` evaluates to
**`false` when `usage` is `null`** (the value the MiniMax API sends).
So the library treats the case "usage is present and null" the same
as "usage is absent entirely" — and routes it to the
"no choices, retry the API" branch.

But the assistant message has already been fully accumulated by
`MiniMaxSseParser` from the prior delta chunks. The recovery code
(`synthesized_message()`) is sitting right there, ready to use.
The library is throwing away a valid completed response and
re-querying the API instead.

### Why the agent looks dead

Three compounding effects:

1. **Streamed content is discarded.**
   `sse_parser.synthesized_message()` is never built. The line
   `messages.push_back(message)` (line ~1531) is never reached for
   the streamed response. The assistant's message — text or
   tool_calls — never lands in the message history.

2. **7-second silent spinner.**
   The retry loop calls `make_http_request_with_retry` with the
   same payload. Each retry waits `1s + 2s + 4s = 7s`. Each retry
   returns essentially the same response (MiniMax is deterministic
   for the same input). To the user: spinner spins, no output,
   no error message about the underlying cause.

3. **Tool-call amnesia.**
   When the streamed response contained a `tool_calls` array, that
   tool call is now lost. After the retries, the agent either
   returns `AgentState::DONE` (clean exit, task never done) or
   returns `AgentState::ACT` with a synthetic error message that
   doesn't reflect what the assistant actually wanted to do. The
   agent has effectively forgotten it was about to call a tool.

### How to reproduce (in icarus)

```bash
$ printf 'list the files in the current directory using the bash tool\n/quit\n' \
    | /workspace/icarus/build/icarus /tmp 2>&1 | tail -20
```

**Expected output:**
```
[/TOOL] bash          ← agent invoked the bash tool
```

**Actual output:**
```
[Warn] [LLM] 'usage' is null in SSE stream — token counts unavailable
>                      ← prompt returns; task never executed
```

(The exact text the agent streams before dying varies — the warning
fires AFTER the streamed text, on the same line.)

### Suggested fix

The gatekeeper for the synthetic-message recovery should be
"the SSE parser accumulated a complete assistant message",
not "the server sent non-null usage". Concretely:

```cpp
bool is_usage_only_chunk =
    config_.stream &&
    (sse_parser.had_text_deltas() ||
     !sse_parser.accumulated_tool_calls().empty()) &&
    (!response_json.contains("choices") ||
     response_json["choices"].empty());
```

That is: if the SSE parser already accumulated a complete response
(text OR tool_calls), AND the final SSE chunk has no `choices`,
treat it as a usage-only trailer — **regardless of what the
`usage` field contains**.

The downstream pipeline (`messages.push_back(message)`,
tool-call processing) already handles a fully-synthesized
message correctly — it just needs the gate to actually open.

### Workaround in icarus

If upstream is slow to fix, icarus can work around this by:

1. **Disabling SSE streaming.** Set `cfg.stream = false`. The
   non-streaming path uses `make_http_request_with_retry` directly,
   parses the full JSON response (which has the real usage), and
   never hits the §Phase 9.10 logic. Trade-off: no live deltas,
   longer first-token latency.

2. **Patching the condition at runtime.** Catch the warning in
   the host sink and re-issue the user prompt until the agent
   produces a non-streaming fallback. Brittle; not recommended.

3. **Adding a post-warning retry in icarus.** Intercept the
   `usage` warning in `ConsoleAgentSink::on_log`, re-submit the
   user message via `agent.submit_user_message()` + `run_one_turn()`
   synchronously (no streaming). Cleaner than #2, still hacky.

### Related upstream references

- §Phase 9.10 comment block (lines 1389-1394) describes the
  intended behaviour — the intent is right, the gatekeeper is wrong.
- §Phase 9.11 added `MiniMaxSseParser::had_text_deltas()` — which
  is exactly the field the fixed gatekeeper needs.
- The MiniMax API quirk (`"usage": null` in the final chunk) is
  documented in `/tmp/test_sse_raw.py` referenced in §Phase 9.10.

## BUG-001 Resolution (daedalus v0.5.1)

**Shipped:** 2026-07-17 (same day as the report)

### What upstream changed

**`src/api/LLMClient.cpp` (line ~1372)** — the buggy inline gate
was replaced with a call to a new helper:

```cpp
if (!response_json.contains("choices") || response_json["choices"].empty()) {
    if (is_usage_only_chunk(config_.stream, response_json, sse_parser)) {
        // §Phase 9.10 / §BUG-001: usage-only final SSE chunk.
        // Build a synthetic single-choice response so the rest of
        // the pipeline (which reads `response_json["choices"][0]`)
        // continues to work. `usage` data is preserved as-is for
        // `update_token_usage`.
        nlohmann::json synth_message = sse_parser.synthesized_message();
        response_json["choices"] = nlohmann::json::array({
            {{"index", 0},
             {"message", synth_message},
             {"finish_reason", "stop"}}
        });
        if (sink_) sink_->on_log(daedalus::LogLevel::Info,
            "[LLM] Stream finished with usage-only final chunk "
            "(recovered via synthesized_message; usage was "
            + std::string(response_json.contains("usage") &&
                          response_json["usage"].is_null() ? "null"
                                                            : "non-null")
            + ")");
        // Fall through to message/tool-call processing below.
    }
    else { /* retry path unchanged */ }
}
```

The new info-level log explicitly distinguishes the recovered case
by reporting whether `usage` was `null` or `non-null` — useful for
operators who previously conflated the two with a single `[Warn]`.

**`src/api/MiniMaxSseParser.h` (line ~108)** — new helper
centralising the gate logic, with an inline truth table comment:

```cpp
inline bool is_usage_only_chunk(
    bool stream_enabled,
    const nlohmann::json& response,
    const MiniMaxSseParser& parser) noexcept
{
    if (!stream_enabled) return false;
    if (response.contains("choices") && !response["choices"].empty()) {
        return false;  // not a no-choices chunk
    }
    return parser.had_text_deltas()
        || !parser.accumulated_tool_calls().empty();
}
```

The fix uses **both** signals — `had_text_deltas()` AND
`accumulated_tool_calls()` — instead of the old single-signal
check on `usage`. This matches our recommended fix verbatim.

Also added: a public getter `accumulated_tool_calls()` on
`MiniMaxSseParser` (previously the field was private), so the
helper above can read it from outside the class.

### Comments

- The upstream commit cites our bug ID (`§BUG-001`) directly in the
  fix's comment block. They treated the report as actionable enough
  to land same-day.
- The fix also demoted the warning from `[Warn]` to `[Info]` since
  the situation is now recovered, not a failure. The old warning is
  kept at `[Warn]` for the still-unrecoverable case (usage absent
  AND no accumulated text/tool_calls).
- The truth table is now exported as a free function, which the
  upstream test suite can exercise directly. Worth checking whether
  new unit tests cover it on the next refresh.

### icarus-side action

**None.** icarus was unaffected by the fix other than benefiting
from the corrected behaviour. No code changes needed in icarus;
the workarounds listed in the original bug report are no longer
required.

### Verified after the fix

```
$ /workspace/icarus/build/icarus --version
icarus (daedalus 0.5.1)
```

Task-execution paths (tool calls) now complete successfully
through the SSE streaming path without the 7-second silent-spinner
stall.

## BUG-002 (daedalus v0.5.1-3-g3e2b888) — `serper_settings_tests` fails when daedalus is built as a CMake `ExternalProject`

**Severity:** Low — test-only failure, no runtime impact on consumers.
Three of the seven `serper_settings` regression tests fail with
`FAIL: !content.empty()` when the library is built in a layout where
the build directory and the source directory are siblings (i.e. the
`ExternalProject_Add` / `FetchContent` pattern that icarus uses).

**Status:** 🔴 **OPEN.** Reported 2026-07-17 by icarus after the
clean rebuild pulled daedalus `main` (v0.5.1-3-g3e2b888).

**Affects:** `tests/test_serper_settings.cpp`. Specifically the
three tests that source-grep `src/tools/SearchTool.cpp` and
`src/core/SettingsMigrator.cpp`. The four other tests in the same
file (the ones that read `examples/settings.json.example`) are
properly guarded with `if (!std::filesystem::exists(path)) return 0;`
and pass cleanly.

**Discovered in icarus:** 2026-07-17 — surfaced on the first
`ctest --rerun-failed` after pulling daedalus `main` into icarus.

### Symptom (in icarus)

```
$ cd /workspace/icarus/build/daedalus && ctest -j12 -E "live-llm"
...
 5/63 Test  #6: serper_settings_tests .................***Failed    0.00 sec
...
95% tests passed, 3 tests failed out of 63

$ ctest --rerun-failed --output-on-failure -R serper_settings
Running Serper settings tests...
FAIL: !content.empty() at .../tests/test_serper_settings.cpp:97
FAIL: !content.empty() at .../tests/test_serper_settings.cpp:112
FAIL: !content.empty() at .../tests/test_serper_settings.cpp:126
```

Line 97 = `CHECK(!content.empty())` after
`slurp(root / "src" / "tools" / "SearchTool.cpp")`
Line 112 = same `slurp` against `SearchTool.cpp`
Line 126 = `slurp(root / "src" / "core" / "SettingsMigrator.cpp")`

All three failures are inside the heuristic-test block; none of the
tests that touch `examples/settings.json.example` fail because they
have an existence guard.

### Root cause

`tests/test_serper_settings.cpp` opens with a project-root heuristic
(lines 51–61):

```cpp
std::filesystem::path find_project_root() {
    std::filesystem::path candidate = std::filesystem::current_path();
    for (int i = 0; i < 6; ++i) {
        if (std::filesystem::exists(candidate / "CMakeLists.txt")) {
            return candidate;
        }
        if (candidate.has_parent_path()) {
            candidate = candidate.parent_path();
        } else {
            break;
        }
    }
    return {};
}
```

That walks up from CWD looking for the first directory containing
`CMakeLists.txt`, then uses that as the source root.

**It assumes the build directory is a child of the source directory.**

In a normal daedalus build (cmake-from-source), CWD is
`build/daedalus-src/tests/`, walking up hits `build/daedalus-src/`
which contains both `CMakeLists.txt` and `src/tools/SearchTool.cpp`.
Works fine.

In the `ExternalProject_Add` layout that icarus uses, the layout is:

```
build/_deps/daedalus-src/    ← source tree
build/daedalus/              ← ExternalProject build tree (separate)
build/daedalus/tests/        ← CWD when the test runs
```

Walking up from CWD hits **`build/daedalus/`** first (because the
ExternalProject configured its own copy of `CMakeLists.txt` there),
so `root` becomes `build/daedalus/` — which has a `CMakeLists.txt`
but **no `src/`**. `slurp(root / "src" / "tools" / "SearchTool.cpp")`
returns `""`, and the subsequent `CHECK(!content.empty())` fires.

The four example-file tests in the same file are unaffected because
they each start with:

```cpp
if (!std::filesystem::exists(path)) {
    // examples/ was deleted in v0.4.2 — skip
    return 0;
}
```

Those three grep tests have no such guard, so they fail when `slurp`
returns empty.

### How to reproduce (outside icarus)

Any CMake project that consumes daedalus via `ExternalProject_Add`
or `FetchContent` triggers it. Concretely:

```bash
git clone https://gitlab.com/leestripp/daedalus.git
mkdir daedalus-fakeproj && cd daedalus-fakeproj

# Minimalist host CMakeLists.txt
cat > CMakeLists.txt <<'EOF'
cmake_minimum_required(VERSION 3.28)
project(fakeproj LANGUAGES CXX)
include(ExternalProject)
ExternalProject_Add(daedalus_ext
    SOURCE_DIR ${CMAKE_SOURCE_DIR}/../daedalus
    BINARY_DIR ${CMAKE_BINARY_DIR}/daedalus
    INSTALL_COMMAND ""
)
EOF

cmake -S . -B build
cmake --build build -j$(nproc) --target daedalus_ext

cd build/daedalus && ctest -R serper_settings --output-on-failure
```

**Expected:** all 7 tests pass.
**Actual:** 3 fail with `FAIL: !content.empty()` at lines 97, 112, 126.

### Suggested fix

Two clean options, in order of preference:

1. **Walk up further, or stop at the directory that actually has
   `src/tools/SearchTool.cpp`.** The test knows what file it wants;
   it should anchor on the file, not on `CMakeLists.txt`:

   ```cpp
   std::filesystem::path find_project_root() {
       std::filesystem::path candidate = std::filesystem::current_path();
       for (int i = 0; i < 8; ++i) {
           if (std::filesystem::exists(candidate / "src" / "tools" / "SearchTool.cpp")) {
               return candidate;
           }
           if (!candidate.has_parent_path()) break;
           candidate = candidate.parent_path();
       }
       return {};
   }
   ```

   This works in both layouts: in-source builds hit
   `build/daedalus-src/`; ExternalProject builds climb past the
   build dir and hit `build/_deps/daedalus-src/`.

2. **Pass `-DDaedalus_SOURCE_DIR=${CMAKE_SOURCE_DIR}` from the
   top-level CMakeLists.txt** and consume it via a generated header
   in the test. Less hacky, but requires touching `CMakeLists.txt`
   and adding a `configure_file` call.

Option 1 is the smallest blast radius and needs no CMake changes.

### Workaround in icarus

None needed — icarus does not run `ctest` against the daedalus
sub-build. The failures only show up if a consumer descends into
`build/daedalus/` and runs `ctest` manually. If/when a CI step is
added that runs daedalus's own test suite from an ExternalProject
layout, this will block CI green. Filed here so it's tracked.

### Related upstream references

- `tests/test_serper_settings.cpp` lines 51–61 (the heuristic).
- `tests/test_serper_settings.cpp` lines 140–145, 175–181 (the
  correct skip-if-missing pattern that the failing tests lack).
- `CMakeLists.txt:404` — the install code references
  `examples/settings.json.example` and emits a `WARNING` when
  missing. That's the only consumer of the (deleted in v0.4.2)
  `examples/` directory, and it degrades gracefully. Not a bug.
- The deletion of `examples/` in v0.4.2 is referenced by inline
  comments in the test file ("examples/ was deleted in v0.4.2 —
  skip"), which suggests the author knew about the layout
  fragility. The fix here is in the same spirit: degrade gracefully
  instead of failing when the assumed layout doesn't hold.
